## 0. Executive Architecture Summary

The system is a high-performance, editorial portfolio and personal publishing platform powered by **Eleventy**, **Node.js**, **Markdown/YAML**, and an **Obsidian-inspired personal admin workspace**.

```text
                              GITHUB REPOSITORY
                         (Canonical Source of Truth)
                         Markdown + YAML + WebP Assets
                                      |
                                      | GitHub API commits
                                      v
                         +---------------------------+
                         |           VERCEL          |
                         |   Unified Production App  |
                         +---------------------------+
                           |                       |
                           v                       v
                  PUBLIC PORTFOLIO            PRIVATE ADMIN
                  • Eleventy output           • Auth/session
                  • Public routes             • WYSIWYG editor
                  • Search index              • Source editor
                  • Media plates              • Note promotion
                  • ShareThis                 • Media manager
                           |                       |
                           +-----------+-----------+
                                       |
                                       v
                              GitHub API / Git
                           Content + assets remain
                           version-controlled in GitHub
```

### Key Architectural Principles
- **No Database Dependency**: GitHub remains the single, version-controlled source of truth. Content is stored as clean Markdown (`.md`) with YAML frontmatter.
- **Unified Vercel Hosting**: BOTH the public portfolio website and the private admin application/API are deployed through **Vercel**. GitHub Pages is no longer part of production hosting.
- **GitHub as Content Backend**: The admin writes content and assets back to the GitHub repository through a secure server-side GitHub integration. Vercel is the hosting/runtime layer; GitHub remains the canonical content/version-control layer.
- **One Production Domain**: Prefer a single Vercel project with public routes such as `/`, `/projects/`, `/blog/`, `/journal/` and a private `/admin/` surface. A separate admin subdomain is optional.
- **Stealth Access**: The admin entry point remains hidden from ordinary navigation and unlocked through the existing `$passcode` command flow. Authentication must be enforced server-side; hiding the URL is not a security boundary.
- **Editorial Bauhaus Design**: Strict adherence to off-white paper (`#f2f0ea`), deep ink (`#111`), hairline rules (`#d4d1c9`), red accent (`#e03c31`), DM Mono, Inter, and numbered navigation.

### Phase 6: GitHub Commit Sync & Powerful Instant Search

- [x] **GitHub Actions Workflow (`.github/workflows/deploy.yml`)**: Automated CI/CD workflow deploying static site build to GitHub Pages on push to `main`.
- [x] **Instant Search Index (`src/search-index.njk`)**: Compiles `/search-index.json` during builds across all published content.
- [x] **As-You-Type Search Engine (`src/_includes/layouts/base.njk`)**: Live token matching across titles, categories, descriptions, and tags with `<mark>` term highlighting.
- [x] **Command Palette Keyboard Controls**: Full `ArrowUp`, `ArrowDown`, `Enter`, `Escape` navigation inside the dropdown search pane (`#search-results-pane`).
- [x] **Stealth `$passcode` Command Mode**: Typing `$` turns the search input into a password field with a `COMMAND` badge, validating `$abantika2026` to unlock `/admin/` silently.

## 3. Stealth Admin Access & Authentication Flow

### Unlocking the Admin Console
1. Hover or click the **magnifying glass search icon** in the top navigation header on any public page.
2. Type `$abantika2026` into the search bar.
   - As soon as the first character (`$`) is typed, the search input automatically masks into a password field, and the status pill changes to `COMMAND`.
3. Press **Enter**.
   - The backend validates the passcode via `POST /api/auth/passcode`.
   - On success, the badge displays `UNLOCKED →` with a red highlight, setting an HTTP session cookie and redirecting to `/admin/`.
   - On failure, the badge displays `DENIED`.

## 4. Production Deployment & Operations Guide

### Option A: Running & Editing Locally
1. Start the local development server:
   ```bash
   node server/admin-api.js
   ```
2. Open your browser:
   - **Public Site**: `http://localhost:8080/`
   - **Admin Console**: `http://localhost:8080/admin/`

### Option B: Deploy BOTH Public Site and Admin to Vercel — REQUIRED Production Path

GitHub Pages is no longer required. Do not build the production architecture around GitHub Pages. The target is one Vercel project serving the public website, `/admin/`, and the production API.

#### Step 1 — Connect the existing GitHub repository
1. Import the existing repository into **Vercel**.
2. Keep the repository as the source of deployments.
3. Do not create a second content repository.
4. Configure the project around the existing Node.js + Eleventy application.

#### Step 2 — Configure the Vercel build
Vercel must be able to:
- install Node dependencies;
- run the existing Eleventy build;
- serve the generated public output;
- serve `/admin/`;
- expose the production API;
- allow the server-side GitHub integration to commit content and media.

Use the existing `package.json`, `vercel.json`, `.eleventy.js`, `src/`, `server/`, and admin implementation as the starting point.

#### Step 3 — Adapt the backend for Vercel
The current local server is:
```bash
node server/admin-api.js
```

Keep that for local development.

For production, the API must run through Vercel-compatible serverless/API handlers rather than relying on a permanently running Express process. Preserve the existing functionality, including:
- `/api/auth/passcode`
- content read/write operations
- `/api/promote`
- `/api/upload-media`
- GitHub synchronization
- any existing preview/rebuild functionality

Do not remove working CMS functionality merely to simplify deployment.

#### Step 4 — Configure production environment variables
In **Vercel → Project → Settings → Environment Variables**, configure the variables expected by the existing code, including:
- `ADMIN_PASSCODE`
- `GITHUB_TOKEN` (if the current implementation still uses it)
- `GITHUB_REPO_OWNER`
- `GITHUB_REPO_NAME`

For production hardening, prefer a least-privilege GitHub App or fine-grained credential when the implementation is ready. Never expose GitHub credentials to browser-side JavaScript.

**Security rule:** Never commit a real token or production secret to this handoff or the repository.

#### Step 5 — Make Vercel the only production web host
Target topology:

```text
https://your-domain/
        |
        +-- Public Eleventy portfolio
        |
        +-- /admin/
        |      |
        |      +-- authenticated admin UI
        |
        +-- /api/*
               |
               +-- server-side API
                       |
                       v
                    GitHub
```

GitHub Pages should NOT serve the production portfolio.

#### Step 6 — Preserve GitHub as the source of truth
The migration to Vercel does **not** move content into a database or make Vercel the canonical content store.

Content remains under:
```text
content/
```

Assets remain in the repository. Admin changes continue to create GitHub commits through the server-side GitHub integration.

#### Step 7 — Remove the GitHub Pages production dependency
After Vercel is verified:
- GitHub Pages no longer needs to serve the public site.
- `.github/workflows/deploy.yml` becomes legacy unless reused for CI/validation.
- Do not maintain two independent production deployment pipelines.
- Remove or disable the deployment portion of the workflow after Vercel is stable.

#### Step 8 — Verify the full production flow
Test:
1. `/` and every public route.
2. Projects, blog, journal and skills pages.
3. Search and `/search-index.json`.
4. ShareThis on applicable detail pages.
5. `$passcode` authentication.
6. `/admin/`.
7. WYSIWYG/source editing and preview.
8. Draft save.
9. Publish confirmation.
10. GitHub commit creation.
11. Vercel redeployment/update.
12. Media upload and public rendering.
13. Note promotion.
14. Failure/retry behavior.
15. Privacy of unpublished/private content.

Private/draft content must never appear in public search, backlinks, related content, sitemap, RSS, navigation, tags, or generated public indexes.

### Recommended Vercel Production Topology

Prefer one Vercel project initially:

```text
Vercel Project: abantika-portfolio
│
├── /                       Public site
├── /about/
├── /projects/
├── /projects/:slug/

├── /skills/
```

## 6. V3.1 Migration Checklist — GitHub Pages → Vercel

This is the implementation sequence for moving the current V3 system to unified Vercel hosting.

### Phase 1 — Freeze the working state
- Commit the current working code to GitHub.
- Confirm the local public site and admin still work.
- Do not delete existing content, server, admin, or Eleventy functionality.

### Phase 2 — Create the Vercel production project
- Import the existing GitHub repository.
- Configure the Node.js/Eleventy build.
- Add required environment variables.
- Confirm a successful Vercel build.

### Phase 3 — Production API
- Keep `node server/admin-api.js` for local development.
- Adapt the existing API to Vercel-compatible serverless handlers.
- Keep GitHub credentials server-side only.
- Preserve authentication, GitHub sync, media upload, promotion, preview, save and publish behavior.

### Phase 4 — Public website
Verify every public route, asset, video, search index, metadata and ShareThis integration on Vercel.

### Phase 5 — Admin
Verify authentication, `/admin/`, WYSIWYG/source editing, preview, draft save, explicit publish, media upload, note promotion and GitHub commits.

### Phase 6 — Privacy
Verify that `published: false` or equivalent private/draft content cannot leak through direct URLs, search, backlinks, related content, tags, sitemap, RSS, navigation or generated indexes.

### Phase 7 — Cutover
- Attach the production domain to Vercel.
- Confirm the public site and `/admin/` work from the production domain.
- Stop relying on GitHub Pages.

### Phase 8 — Cleanup
- Remove/disable the GitHub Pages deployment workflow.
- Keep GitHub Actions only if useful for CI/validation.
- Update README and documentation to state that Vercel is the production host.
- Rotate temporary credentials used during migration.

### Definition of Done

```text
GitHub
  = canonical source of truth

Vercel
  = public host
  = admin host
  = API/runtime

GitHub Pages
  = no longer required
```

The user should be able to edit from `/admin/`, commit the change to GitHub, publish it, and see the public Vercel site update without maintaining a separate GitHub Pages deployment.
