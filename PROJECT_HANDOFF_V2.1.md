# 0. Executive Architecture Decision

The project has **two deployment surfaces connected to one GitHub repository**.

```text
                         GITHUB
                    SOURCE OF TRUTH
                 Markdown + YAML + Assets
                           |
             +-------------+-------------+
             |                           |
             v                           v
        VERCEL ADMIN               GITHUB ACTIONS
        private UI/API             Validate + Eleventy
        WYSIWYG + Source           Build + Deploy
        Preview + Media                  |
        GitHub Auth                       v
             |                       GITHUB PAGES
             +--------------------> PUBLIC WEBSITE
```

## Mandatory interpretation

- **GitHub** is the permanent source of truth.
- **GitHub Pages** hosts the public portfolio.
- **Vercel** hosts the private admin application and server-side API.
- **Eleventy** generates the public static site.
- **Markdown/YAML** are the canonical content representation.
- **WYSIWYG** is a required Version 1 editing interface.
- The admin should be **inspired by the ease and mental model of tools such as Obsidian**, but **Obsidian compatibility is NOT a requirement**.
- There is **no database**.
- Do not introduce Supabase, Firebase, WordPress, a traditional CMS, or a paid CMS.
- Do not use LinkedIn OAuth/API or automatic LinkedIn publishing.
- LinkedIn sharing is handled by the supplied ShareThis integration.
- The public website must remain functional even if the Vercel admin is unavailable.

# 2. Phase 5 — Local Admin Foundation

## Objective

Stabilize the existing local admin workspace and use it as the foundation for the production Vercel admin.

The admin is a **personal publishing workspace**, not a generic SaaS dashboard.

Maintain the same visual language as the public portfolio:

- off-white paper;
- black typography;
- grey technical rules;
- restrained red/orange accents;
- editorial grid;
- monospace metadata;
- numbered sections;
- generous whitespace;
- minimal UI;
- no generic blue dashboard;
- no glassmorphism;
- no excessive rounded cards.

## Admin sections

```text
Dashboard
About
Projects
Blog
Journal
Notes
Pages
Media
Settings
```

## Core actions

The user must be able to:

- create content;
- edit content;
- save drafts;
- preview;
- publish explicitly;
- upload media;
- insert media;
- organize content;
- link content;
- inspect backlinks;
- change metadata;
- delete content safely;
- navigate between documents quickly.

Publishing must never happen merely because the user typed or saved.

Local development should continue to support:


with:

# 6. Obsidian-Inspired Usability — NOT Compatibility

## Requirement

The admin should be **as easy and flexible to use as a personal knowledge-management workspace such as Obsidian**.

This is a UX requirement, not a compatibility requirement.

Do NOT:

- require Obsidian for testing;
- make Obsidian compatibility a definition of done;
- reproduce the Obsidian interface;
- implement obscure Obsidian-only features merely for compatibility.

Instead, use the useful mental model:

```text
open workspace
    |
create document
    |
write freely
    |
organize
    |
link documents
    |
add media
    |
preview
    |
publish
```

The user should not need to understand CMS concepts such as records, database schemas, or content IDs.

# 10. Phase 7 — WYSIWYG Editor

## Non-negotiable

**WYSIWYG is a Version 1 requirement.**

The user must be able to write normally without learning Markdown.

However:

> Markdown remains the canonical storage format.

WYSIWYG is a visual editing layer over Markdown.

---

# 11. Three Editor Modes

Every substantial document should support:

```text
EDIT
SOURCE
PREVIEW
```

### EDIT

Visual WYSIWYG editing.

### SOURCE

Raw Markdown and YAML.

### PREVIEW

Actual rendered portfolio page using production templates.

Optional split views:

```text
SOURCE | PREVIEW
```

and:

```text
WYSIWYG | PREVIEW
```

Do not build a separate fake preview renderer.

---

- paragraphs;

- unordered lists;
- ordered lists;
- blockquotes;
- inline code;

- horizontal rules;
- images;

Optional:

- task lists;


Use Tiptap or another mature structured editor internally if appropriate. The user does not need to learn the editor framework.
